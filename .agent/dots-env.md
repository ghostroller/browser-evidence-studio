# dots 环境约定

## 适用范围
- 仅当可信的当前任务环境信息明确标识为 **dot 云端桌面** 时适用；不能仅凭 Linux、工作目录、容器或“云端”字样推断。
- 普通 Linux、用户电脑、注册 Remote 和 Codex Cloud 编码环境不自动适用；无法确认时不启用本文件。
- 本文件补充根目录 `AGENTS.md`：dots 环境的日常提交与推送采用下述自主交付流程，不逐次要求人工确认；当前用户指令、权限边界和安全要求优先，不扩大仓库或凭据访问范围。

## 自我监督与人工介入
- 在用户任务范围内，由 agent 自主拆解目标、实施、检查差异、执行验证并复查结果；遇到可恢复问题自行定位和修正，持续推进到可验收节点，不把日常执行与检查交回用户。
- 需要新权限、存在重大产品取舍、必须人工验收或遇到无法自行解决的阻塞时，集中说明证据、影响和最小待决问题，请用户确认；仅审查、仅本地修改或暂停发布等明确限制始终优先。

## 工作重点：前端、交互与集成验证
- 在本轮任务范围内，优先利用可见云端桌面完成前端、交互和视觉相关实现，并补充面向真实应用的集成测试，形成“实现—桌面操作—观察反馈—修正”的闭环。
- 重点关注布局与可读性、导航和表单、状态反馈、焦点与键盘操作，以及跨页面或窗口的完整用户路径；按改动涉及的风险验证中断、取消、重复操作、错误恢复和重启后的行为。
- 这是一种环境优势下的工作侧重，不扩大用户任务：纯后端任务不为使用桌面而附加 UI 改动，必要的单元测试、服务测试和定向回归仍须完成。

## 桌面执行与验收
- 本地 Web 前端与集成自动化后续优先使用项目现有的普通 Puppeteer + 隔离 Chromium，通过已授权的项目测试入口检查真实 DOM、样式、截图、控制台和网络反馈；复用现有技术栈，不另引入自动化平台，也不以云端浏览器工具能打开 localhost 为前提。
- 操作前核对目标身份，区分 Electron UI 宿主、受控业务浏览器和历史回放；测试当前 profile 或录制实例时，不能用相同 URL 的新页面替代实际目标。
- 涉及 Electron 界面、原生窗口或桌面集成时，在 dot 的可见云端桌面运行当前代码构建的实际应用，保留原生电脑操作工具及必要的人工验收；独立 Chromium 预览、隐藏接口或后台测试不能替代实际 Electron 验收。
- Puppeteer 优先约定仅适用于已授权的本地开发与项目测试，不扩展到一般网页浏览；保留应用安全配置，不关闭 webSecurity，也不借其他工具绕过访问拒绝或网络限制。
- 编写代码、Git、构建、后端测试、等待和日志检查优先直接使用执行工具；GUI 用于真实视觉和交互验证，环境确有要求时也可用于启动应用，不用 GUI 展示终端进度。
- 按根约定先做受影响路径的最小回归，再做相关用户路径的集成验证；按需保留脱敏桌面截图或其他可追溯证据，遵守根约定的隐私和提交边界。
- 交付说明实际源码/构建身份、验证步骤、观察结果及未测或失败范围；构建或单元测试通过不等于交互验收通过，功能路径通过也不等于用户接受其体验。
- 纯文档变更检查差异、链接和 `git diff --check`，无须因此重跑完整功能测试。

## Git 与发布通道
- 开始时核对 Git 根目录、HEAD、工作树状态、远端地址、当前分支及本轮目标分支；通过已连接的 GitHub 插件只读核对仓库权限和最新远端提交。保留已有改动，不自动丢弃或覆盖。
- dot 云端桌面优先使用当前已连接且对目标仓库有写权限的 GitHub 插件发布；终端 Git 继续用于本地差异、验证和历史管理。插件授权不等于终端 Git 已获认证，不默认要求用户手工配置 PAT，也不每轮探索 SSH 或重建认证流程。
- 发布范围限定为 `ghostroller/browser-evidence-studio` 和当前获授权任务；本约定不证明插件已连接、权限有效或本轮已获发布授权。插件不可用时报告确切阻塞，使用受支持的连接／重连流程，不绕过访问拒绝。
- 不搜索、读取或下载 Library 中的凭据，不从历史文件路径恢复令牌，也不把令牌配置进本地 Git。新建或扩大持久访问仍需遵守当前授权与逐次确认要求；不擅改全局凭据配置或扩大仓库范围。
- 令牌及其编码、转义或其他可还原形式不得进入仓库、聊天、命令输出／日志或 URL；不把凭据路径或其他环境专属绝对路径写入仓库、日志或交接。需要秘密输入时交由用户通过安全流程完成，不索要聊天中的令牌。
- 插件通过 GitHub API 创建 blob、tree、commit 并更新分支，不能据此声称原生本地提交对象已原样推送。重建提交会产生新 SHA，Author／Committer 由接口和连接身份决定；接口未提供身份参数时不得承诺保留本地身份。开始重建发布前说明该差异并获得用户对本轮方式的认可。
- 以刚核验的远端提交为父提交，仅上传已审查的跟踪文件差异，不混入证据、私有资料、凭据或构建产物。可以将已验证且同属本轮交付的本地提交汇成一个 API 提交，在正文记录来源提交 SHA 和发布方式；这只是来源说明，不表示原提交历史已进入远端。
- 创建远端 tree 后核对其完整 tree SHA 与预期本地最终树；提交后、更新分支前再次读取目标分支。若远端前进，保留双方改动并重新审查，不把旧完整树覆盖到新父提交上。分支更新必须非强制；保护规则拒绝时按规则处理。
- 发布后通过插件回读目标分支、提交父节点、tree 和文件内容／blob SHA，核对预期 API 提交及最终内容。原本地提交 SHA 不同是预期现象，不能仅凭差异判为失败，也不能只凭 API 创建对象就宣称分支发布完成。
- 如需同步本地分支，先用安全分支保留原本地历史，再以核验过的远端对象同步；不擅自 reset、clean 或改写原历史。无法同步时明确记录本地与远端不同的提交身份及内容核对结果，避免下一轮重复发布。

## 提交身份与协作署名
- 本地 Git 提交仍使用 Author 为 ghostroller、Committer 为 dot；提交正文末尾另加 `Co-authored-by: dot <运行时配置的 dot 邮箱>`，与正文之间空一行。尖括号内的说明是占位符，实际提交须替换为已配置邮箱。
- 邮箱仅从用户单独授权的当前环境配置读取，不把任何具体邮箱写入受版本控制的文档；署名邮箱不是登录凭据，发布后会随提交元数据公开。
- 本地提交优先使用仓库本地的 `author.name` / `author.email` 和 `committer.name` / `committer.email`；不修改全局身份。提交前用 `git var GIT_AUTHOR_IDENT` 与 `git var GIT_COMMITTER_IDENT` 核验实际身份，并让协作署名与 dot 的 Committer 身份一致。
- API 提交在接口支持且已获授权时设置身份；接口不支持时明确披露实际身份差异，正文可沿用已核验的 dot 协作署名。协作署名不等于原生 Author／Committer 保留，也不保证 GitHub 账户关联或签名验证。
- 缺失或不匹配时先修正已获授权的本地配置，不能猜测邮箱或提交占位符；署名约定不扩大任务权限，也不授权改写历史。

## 提交、推送与人工审查
- 按任务范围、风险和仓库规则自主选择直接向 main 提交并推送，或在独立分支提交并推送；明确、低风险且已验证的变更可直接进入 main，需要隔离验证或人工确认的功能走分支与 PR，不机械要求用户逐次批准。
- 需要人工确认的功能发起 PR 请求人工审核，说明改动、验证证据和待确认事项；审核完成前不自行合并，也不以直推 main 绕过审核或分支保护。
- 每个提交聚焦一个可说明、可验证的变更，避免混入无关改动；本地优先多个小提交，API 发布可按上节将同一已验收交付包汇成一个带来源说明的提交；允许多个小提交一起推送，但至少在每个可验收功能节点完成后推送一次。若发布受限，记录已完成节点及阻塞，不谎称已交付。
- 提交和推送前自查差异、测试结果、敏感信息与目标，只按明确路径暂存；使用非强制推送，不覆盖他人提交。
- 若远端前进，先核对并保留双方改动，按本轮授权处理同步或冲突，重跑受影响验证后再发布；不擅自 reset、clean 或强推。
- 实际发布后读取目标远端的精确 SHA，与预期发布提交核对（API 提交另核对完整树与本地内容），并检查本地工作树，报告剩余改动；存在 CI 验收要求时核对该 SHA 的结果。
- 只读查询、认证成功和 dry-run 均不证明写入成功；只有实际写入及远端核验完成后，才报告已推送。
