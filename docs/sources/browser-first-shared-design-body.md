## 原回答正文

我赞成“Web 工作台优先、Electron 作为桌面宿主”的方向，但不建议把“立即完全迁移到纯 Node＋外部 Chromium”当成改善界面的前提。

对当前项目，收益最高的顺序是：

先让同一套前端在普通浏览器里连接真实服务运行，建立快速的 DOM／样式／截图反馈循环；再把历史回放变成标准 Web 组件；最后根据实际收益，逐步抽出独立 Node 后端和外部 Chromium 运行时。

这样不是又启动一次全项目重写，而是先解决你现在最痛的开发问题，再决定需要拆到什么程度。

## 一、先看代码：你的判断有依据，但不是“Electron 不能被 Agent 测试”

### 1. 前端与 Electron 的第一层连接，其实很薄

目前 src/preload/ui.ts 主要只暴露：

```typescript
studio.call(method, body)
studio.onChanged(listener)
studio.bounds(rect)
```

因此，把前端调用改为可注入的客户端，并提供 IPC 和 HTTP 两个适配器，是现实可行的第一步。不需要先推翻录制、任务资料或验证器。

但是，当前组件直接使用全局 window.studio，并且 call 的类型基本是 `string → Promise<any>`。它在 Electron 中方便，到了双端运行时，就容易出现“Web 端也声明一个同名对象，但支持行为不一致”的隐性分叉。应将它收敛为同一个有类型、可验证的应用客户端，而不是到处增加 isElectron 判断。

### 2. 真正难拆的，是后端和浏览器宿主，不是 React

当前 Studio 同时依赖：

```text
项目／环境／会话
录制和执行
WebContentsView
Electron Session
StudioWindow
菜单、剪贴板和外部链接
```

构造时也直接创建依赖原生窗口的 ReplayHost。所以，现有后端还不是一个可以直接换成 node server.js 启动的服务。只把 preload 换成 fetch，不能完成你设想的全部架构。

相对有利的是，CaptureCoordinator 的主体已经围绕 Puppeteer Page、CDPSession、网络事件、源节点和证据存储工作，并没有直接导入 Electron。录制核心有较好的复用基础，只是页面身份仍含必填 webContentsId，以及运行时启动、导航和清理需要适配。

### 3. 现在的布局，跨了两套呈现系统

工作台是 React DOM；嵌入的实时页面和历史回放，却是独立的原生 WebContentsView。

BrowserPresentation 需要不断把 DOM 的 bounds、遮罩和拖动状态发给主进程，用来控制原生 view 的位置与显隐；ReplayHost 又通过 executeJavaScript 构造另一套页面、播放器和选择层。

这解释了为什么普通的布局变化会牵扯：

弹窗遮挡、原生页恢复、焦点、窗口可见性、坐标、异步关闭、回放状态。

WebContentsView 不是工作台 DOM 里的普通子元素，它有自己的 WebContents 和布局管理方式。因此，仅检查工作台 DOM，并不能完整判断嵌入页面是否被原生层遮挡。这不是换个提示词就能消除的结构成本。
[Electron](https://www.electronjs.org/docs/latest/tutorial/web-embeds)

### 4. 但当前项目已经有 CDP，不必所有测试都走 OS 坐标

src/main/app.ts 已经启用本机调试端口，并读取 DevToolsActivePort 获取连接；项目也已经使用 Puppeteer。因此：

“Electron 应用只能通过 computer use 测试”不成立。当前已经具备一部分更精确观察和控制的基础，只是没有充分组织成日常 Agent 开发入口。

Playwright 也提供实验性 Electron 自动化，可以取得页面、操作 DOM、读取 console 和截图。但它对原生系统对话框仍有边界；引入 Playwright 不是本次改造的必需条件，也不意味着应该替换现有业务 Puppeteer。
[Playwright](https://playwright.dev/docs/api/class-electron)

所以，我会同时做两件事：改进现有 Electron 的 DOM 调试入口，并让共享工作台可以运行在浏览器。 前者可以更快起效，后者减少长期的宿主耦合。

## 二、你设想的架构可行，但要明确区分三种“浏览器”

这是决定改造成本的关键。

| 对象 | 用途 | 推荐处理 |
| --- | --- | --- |
| 工作台浏览器 | 保存点、存档、字段、环境管理、结果展示 | 同一 React UI，可运行在 Codex 内置浏览器或普通浏览器 |
| 受控目标浏览器 | 登录网站、人工示范、录制、执行脚本 | 由后端管理的 Electron guest 或外部 Chromium |
| 历史回放文档 | 时间轴播放、历史元素选取、注释 | 标准 Web 回放组件，放在严格隔离的文档中 |

### 工作台放进 Codex 内置浏览器：是有价值的

官方目前支持在内置浏览器中打开本地 Web 应用；Developer mode 可以在获授权的连接中检查 DOM、应用样式、console 和网络。这比只获取 OS 截图和坐标，更适合反复修改表单、滚动区、弹窗和布局。 但要先确认你当前客户端与账户实际开放的能力，不能仅因页面能打开，就假定全部开发工具已经可用。
[OpenAI Developers](https://developers.openai.com/codex/app/browser)

### 受控 Chromium：不等于 Codex 展示工作台的浏览器

需要特别避免这个误解：

在 Codex 内置浏览器打开同一个业务网址，不等于正在操作本项目已经登录、正在录制的那一页。

它们可能有不同的 profile、Cookie、页面 ID 和执行上下文。工作台与目标运行时应通过明确接口联系；开发 Agent 要检查目标页，必须连接实际受控的那个目标，而不是复制网址打开一个替身。

### 任意业务网站，也不能简单放进工作台 iframe

第三方网站可能禁止嵌入；即使可以显示，跨源策略通常也不允许父工作台直接读取其 DOM。不能通过去掉响应头、关闭 webSecurity 或反向代理改写整个站点来解决。
[Electron](https://www.electronjs.org/docs/latest/tutorial/web-embeds)

所以，Web 开发模式的第一版可以是：

```text
Codex 内置浏览器：工作台、资料编辑、历史回放
独立受控 Chromium 窗口：真实业务网站
Node／伴随服务：连接两个界面，维护统一身份与业务状态
```

如果坚持把目标 Chromium 的画面也传回工作台，可以做屏幕流，但那是另一项工程。传回来的像素不会自动变成可被 Agent 查询的 DOM，还会增加输入法、焦点、缩放、拖放、文件选择和延迟处理。对你目前的人力约束，我不建议先做这个。

## 三、推荐的目标架构，以及应该暂缓的部分

建议最终形成：

```text
共享 React 工作台
    ├─ 普通浏览器宿主
    └─ Electron 桌面宿主
               ↓
类型化应用接口与共享用例服务
               ↓
资料／证据／版本／执行／核验
               ↓
BrowserRuntime
    ├─ ElectronRuntime：保留嵌入体验和旧登录环境
    └─ ChromiumRuntime：外部可调试浏览器
```

历史回放作为共享 Web 模块运行，不再为两端各实现一个播放器。

其中，Electron 最后可以主要负责安装、启动、窗口、文件对话框和系统集成；但如果最终仍要保留原生嵌入浏览器，它就仍需要一个 Electron 专用的 runtime/presentation 适配器。“薄壳”不等于一点专用逻辑都没有。

### 为什么我不建议立刻全部换掉？

因为当前最容易得到的收益，与最昂贵的工作不是同一件事：

| 改动 | 对当前问题的价值 | 成本判断 |
| --- | --- | --- |
| 给现有 Electron 提供可靠的 DOM、截图、console 调试入口 | 立即减少部分 OS 操作 | 较小 |
| 同一工作台跑在浏览器，连接真实服务 | 直接改善多数界面开发 | 最值得先做 |
| 历史回放变成标准 Web 组件 | 直接改善回放、选取和注释调试 | 中等，需处理隔离 |
| 整个后端改为独立 Node，新增 Chromium provider | 改善部署、隔离与目标浏览器调试 | 较大，需逐步验证 |
| 完整远程浏览器画面嵌入、云端多用户 | 并非当前核心需求 | 暂缓 |

不能把后两项全部完成，作为看见第一版 Web 工作台的条件。 否则你会再次投入很多小时，得到一堆接口和搬迁提交，却还没有改善最痛的反馈循环。

## 四、必须提前设计的三条边界

### 1. 现有 Agent HTTP API 不能直接当成高权限工作台 API

当前 Electron UI 经过可信窗口检查后，以 source:'ui' 调用业务；现有 HTTP 接口则面向 Agent，使用任务授权，并限制创建项目、环境、控制等能力，还严格校验 Host、Origin 和 Bearer。

迁移时不能：

```text
浏览器发 method/body/source=ui
→ 后端全部相信
```

也不能仅为了让 Vite 连通，就打开宽泛 CORS 或把本地 Agent token 写进前端配置。

需要区分三种主体：

已配对的本地工作台、受任务范围约束的业务 Agent、只读隔离回放。

首批只开放明确的合成开发实例，使用一次配对、当前实例身份、严格来源校验和最小操作集合。浏览器刷新、重连和重复提交仍走既有 operationId 与版本冲突机制。

### 2. 旧 Electron 登录环境不能直接交给 Chrome

新增外部 Chromium 时，应明确记录 provider，旧环境继续由 Electron adapter 使用原 partition/storageRef；新 Chromium 环境使用专门的 user-data-dir。

不要为了无缝切换，移动、改名或直接复用 Electron 的活动 profile 目录。 Chrome 官方对默认 profile 的远程调试也已增加限制，明确建议使用非默认目录和适当的测试浏览器。
[Chrome 开发者](https://developer.chrome.com/blog/remote-debugging-port)

现有账号状态能否迁移，是单独的兼容问题，不是前端 Web 化的必要前置。

### 3. 历史回放必须保持隔离，不能直接注入管理页面

当前 ReplayHost 的隔离不是多余代码：它拒绝权限、导航和外部资源，并按回放代际检查资源请求。迁入浏览器后，这些约束仍要存在。

正确方向是将可信播放器、隔离回放文档和后端来源验证分开，通过有身份的消息传递选择结果。不能为了便于查 DOM，把原网页 HTML 直接插进拥有管理权限的 React 页面。

## 五、其他项目有没有这样做？

有成熟的双端架构与 Agent 开发实践可借鉴，但没有足够证据支持“Electron 项目都在因为 AI 全面迁移 Web”这个结论。

### OpenCode：与你的设想最接近的参考

我检查了当前官方仓库：桌面包已经使用 Electron，并依赖共享的 @opencode-ai/app；同时官方提供 Web 客户端和独立 HTTP 服务。
[开源代码 +1](https://opencode.ai/docs/web/)

更有参考价值的是其 packages/app/AGENTS.md：

- 本地界面修改要求分别启动后端和 UI 服务。
- 明确打开 localhost 验证本地 UI，而不是看不反映本地修改的代理页面。
- 浏览器自动化采用“打开页面 → 读取交互快照 → 点击/填表 → 页面变化后重新观察”的循环。

值得借鉴的是这个开发结构，不是其 Bun、Solid 或 monorepo。 OpenCode 也不承担你这个项目的任意网页录制、历史源节点和离线资源保真，不能把它看成可直接移植的完整方案。

### VS Code：证明运行时分层并不新，也不必一次重写

VS Code 官方在 2022 年就介绍过 browser、node、electron-sandbox 等代码边界及渐进迁移。它说明共享 Web 工作台与桌面能力隔离是一条成熟工程路线，但这项实践早于目前这轮 Agent 热潮，不能虚构成“为了 AI 才改的”。
[Visual Studio Code](https://code.visualstudio.com/blogs/2022/11/28/vscode-sandbox)

### OpenAI 的 harness 实践：更直接解释你目前缺什么

OpenAI 的工程文章描述了让应用可以按 worktree 启动，并把 CDP、DOM 快照、截图、导航和日志直接提供给 Agent。重点是让 Agent 能直接观察产品并验证自己的修改，而不是依赖人转述结果。
[OpenAI](https://openai.com/index/harness-engineering/)

对你的项目，值得学的是这条反馈链，不是复制整套观测平台或再建立无限 review 循环。

## 六、为什么已经改这么多轮，效果仍然差？

我认为是几个因素叠加，但当前优先级已经变了，不应继续主要归咎于“需求没写清楚”。

| 因素 | 当前判断 |
| --- | --- |
| Agent 的观察与反馈环境 | 当前最值得投资。很多普通界面问题，要到重型 Electron/原生操作阶段才暴露 |
| 应用边界和状态组织 | 同样重要。页面编辑、原生布局、浏览器控制和录制生命周期仍高度关联 |
| 需求与视觉标准 | 早期有明显缺口；现在13/14已较明确，下一步需要少量真实界面基准，而不是再写几十页 |
| 功能复杂度 | 客观很高。这是录制、离线还原、资料编辑、执行和证据验证的组合，不是普通管理系统 |
| Agent 的设计和验收判断 | 确实不足。把可点击、能完成、测试通过，当成布局合理和操作自然 |
| 模型能力 | 可能影响整体判断，但单凭结果无法分离其影响；换强模型不能替代真实反馈循环 |

### 这不是泛泛而谈，当前记录已经提供了证据

本轮实现映射区被布局挤成零高，是到了真实 Electron 数值旅程才发现。独立操作又遇到可访问节点/坐标滞后、原生下拉操作失败和多次重新观察。这些是在调试工具和宿主边界上付出的成本，不是业务需求本身要求的成本。

另一方面，独立报告仍提到例证主要显示 UUID/bound、添加现场与最终绑定需要几个阶段、表单很长。这些即使移到浏览器，也不会自动变好。 它们需要 Agent 真正看见界面，在同一个业务任务里反复修改，而不是继续根据“有按钮、有字段、有成功通知”验收。

我前几轮的建议也有一处失衡：不断强化最终的独立复走和桌面证据，却没有足够早地把低成本的日常 UI 观察建立起来。 最终验收很重要，但不能代替开发过程中每几分钟就能进行的反馈。

### 更强模型应当放在哪里？

建议让较强模型承担：

边界设计、首条可运行纵向、关键 UI 状态的取舍和首次视觉审查。

之后明确的界面修改、适配和回归可以由成本合适的模型完成。不要再让强模型常驻做 Git、等待和转述；也不要认为提升思考强度就能补足它看不到真实页面的问题。

你不希望增加太多人力，比较合理的人工投入是：只确认三个关键界面状态，而不是亲自跑整个测试矩阵。

这三个状态可以是：默认保存点页、旧存档只读/派生页、字段选择及错误结果页。Agent 先做出真实页面，你给一次集中反馈，之后自动化保护这个基准。

## 七、建议怎样重构：先买到收益，再扩大范围

### B0：先证明当前工具能够观察

核对内置浏览器访问 localhost、读取 DOM/样式、截图、console 和请求的实际能力与权限。与此同时，把当前 Electron 的 UI target、业务 target、回放 target 明确列出来，验证已有 CDP 能完成什么。

这一阶段不能演变成另写一套 Agent 平台。

### B1：同一工作台在浏览器连接真实服务

先抽出小型 WorkbenchClient，保留 IPC adapter，新增受保护的 HTTP adapter；同一 React 页面通过 Vite 热更新运行。

暂时可以保留 Electron companion 承载未抽出的服务。首批就必须完成真实保存点编辑、复制、存档版本与刷新回读，不能只显示 mock 页面。

第一阶段的验收不是“架构目录建好了”，而是 Agent 已经能在浏览器里改界面、看效果、正常操作，并确认真实持久结果。

### B2：把历史回放与元素选取变成共享 Web 模块

从当前 ReplayHost 中提取播放器、精确定位和选择层，复用已有资源准备、源节点模型和命令代际，不重新造 rrweb。

完成：

```text
打开历史 → 播放/暂停 → 定位 → 点选节点
→ 绑定字段 → 固定版本 → 刷新回读
```

这一步能直接改善你最关键的一组交互的可观测性。

### B3：再提取纯 Node 后端与 Chromium provider

这时才逐步解开 Studio 对 Electron 的依赖，保留现有领域模块。外部 Chromium 首先验证一条完整链：专用环境、导航前安装采集、录制、源节点取样、停录、离线回放和执行。

做到没有 Electron 进程仍能成立，才称为纯 Node 后端。 现有 browser:baseline 也仍启动 Electron，不应当作已经拥有独立 Chromium adapter。

### B4：保持双端，但不维护两套产品

同一业务服务、同一前端、同一回放模块；平台差异由 adapter 和能力报告处理。

Electron 从 B1 起就保留小型冒烟验证，不能最后才发现文件路径、旧 profile、下载或退出不兼容。完整长测按实际改动影响执行，不必每次 CSS 修改都重新跑半小时。
