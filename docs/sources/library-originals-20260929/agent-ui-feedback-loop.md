# Agent 前端反馈循环：首批实施与验收

日期：2026-09-30。配套决策：`docs/architecture/browser-first-workbench.md`。  
目的：先证明“Agent 更容易看见并修正产品”，不把这次任务变成另一个月的跨端框架重写。

## 0. 首批边界

实施 B0/B1，准备 B2 的共享回放接口和风险验证。首批必须交付真实浏览器中的同一工作台、真实服务、真实保存/回读和视觉证据；不接受仅Storybook、全量mock或静态截图作为完成。

若B1已用很小改动接通真实回放模块，可以完成第一条历史选择纵向；否则明确剩余B2工作，不暗中以“只读截图”冒充DOM回放。

**不要在首批开始以下工作：**完整外部Chromium provider、全profile迁移、视频流远程浏览器、云部署、多用户权限平台、全量协议重写、任意框架/构建器更换、重新设计13/14的数据对象。

## 1. 开工前只核对必要事实

- 当前Git根、HEAD、dirty、已存在开发服务和测试实例；`63029811...`只是审查基线，不是reset指令。
- 本机Codex内置浏览器/Developer mode的实际能力与授权；不能从文档推定本账户已经启用。
- Node/npm/lock及现有Puppeteer/CDP入口；不默认安装另一套浏览器驱动。
- 单个隔离合成数据根；业务账号、已有原件、正在运行profile不作为迁移实验对象。
- 此前13/14交互的3个代表状态，选一个固定合成资料样本和一个空根入口。

记录B0实测结果：能否打开本机URL、取得DOM/样式/截图、实际正常点击/输入、读console与请求；哪个步骤仍需OS操作。若不能连接内置浏览器，先验证已有Electron CDP路径或受控测试浏览器，并准确报告工具限制。

## 2. 一条命令提供的开发实例

建议入口名为 `npm run dev:workbench`，也可以沿项目命名约定；命令实现之前不要在文档里把它写成已存在。

启动器需要做：

1. 为本次实例分配数据根、UI/服务端口与目标runtime身份。业务writer只有一个，UI和其他客户端复用服务。
2. 开启真实服务、当前React开发服务；遇到已运行实例，核对manifest与进程而不是每次全部kill重启。
3. 输出一行可打开URL和一份短实例清单：instanceId、工作树/源码、frontendOrigin、backendOrigin、backendKind、runtimeProvider、BES_DATA、就绪状态、日志位置。凭据另保存在受保护文件，不进入普通日志。
4. 后端尚用Electron时明确`backendKind=electron-companion`。不要把“不显示Electron窗口”称为“纯Node”。
5. 配对完成后Web UI可以进行本次显式允许的管理/编辑，不复用业务Agent token冒充用户。非配对页和历史回放都没有这些权限。
6. Ctrl+C/显式结束只清理本实例拥有的测试进程；正在保存的材料按已有flush/取消规则处理。失联后通过instanceId/operationId恢复，不重复创建资料。

允许利用现有start-agent/product-demo逻辑，减少脚本重复。入口应短且专用于本项目，不建设通用任务编排服务。

## 3. 首个真实纵向

使用同一组页面和同一数据服务：

```text
Web工作台打开
→ UI创建项目或打开隔离合成任务
→ 管理/选择工作副本
→ 从已归档合成现场创建/打开保存点
→ 编辑名称、字段说明与纯文字注释
→ 复制卡片并确认焦点在副本
→ 保存固定版本
→ 刷新并重新打开同一资料
→ Electron工作台读取相同内容（同一后端或服务先正常退出后独占打开）
```

源录制可以由已有recording fixture合法创建，作为布局/编辑场景的外部输入；不得预填被测试的项目/字段/版本来让上述创建路径通过。最终产品全程验收仍要求用户从空根完成同一业务任务。

如果采用共享后端同时打开Web与Electron，两端的写入须由服务端草稿修订/幂等规则仲裁，不同时启动两个writer。验证两个客户端编辑冲突不是互相静默覆盖。

不得为了让Web模式“全绿”返回虚假的browser状态、永远成功的授权或模拟保存结果。真正不可用的native能力标明，并提供当前runtime的明确入口。

## 4. 交互观察方式

### 4.1 允许且推荐

- 读取DOM、role/name、关联label、computed style、bounding rect、scrollHeight、实际命中元素。
- 正常locator点击、填表、键盘、滚轮/scrollIntoView；页面变化后重新取元素。
- 在允许的合成实例检查console、请求和服务端按requestId关联的日志。
- 截图判断层级、留白、按钮分组、拥挤和文案；DOM数据只说明结构，不代替视觉判断。
- 调整可重复viewport，复查默认与窄窗口；测试DPI/native差异时再启动Electron专项。

### 4.2 不能拿来证明UI可用

- 用隐藏dispatch先创建字段、关联或版本，再点击一个“已完成”按钮。
- 直接设置React state、修改表单之外的持久模型或用evaluate替代正常按钮动作。
- `force:true`点击不可见/被遮挡控件后说交互通过。
- 只查元素存在，不查尺寸、裁切、命中、滚动和保存后的数据。
- 前端只接mock，而将真实服务兼容性留给最终安装包。

调试时可以用受控内部信息定位原因，但最终成功证据要来自正常生产交互路径。配置测试账号或注入可控故障是基础设施准备，与伪造业务资料分开记录。

## 5. 三个可见状态先对齐

不要求重新制作完整设计系统。每个状态用当前真实页面给出截图和必要几何数据：

| 状态 | 必须容易判断的问题 |
|---|---|
| 保存点默认页 | 当前项目/卡片是谁？最常用新增/字段/注释动作在哪？是否与草稿/存档发布混在同一层？ |
| 存档只读与派生编辑 | 现在看的是哪一版？哪些内容不能改？继续编辑后新副本是否成为明确当前对象？ |
| 字段选择与错误结果 | 当前选择用于哪个字段？取消会不会清旧绑定？错误值和来源不足是否可理解，返回是否保留上下文？ |

可以由Agent先提出一个首选布局并落实，再让用户只评论三个状态；不要求用户逐个测试所有故障组合。确认以后保留固定场景截图基线，不每次因局部修复重新布局整页。

## 6. 首批验收清单

| ID | 验证项 | 必须记录的结果 |
|---|---|---|
| F01 | 浏览器能力 | 实际本机URL、工具/权限、DOM与截图能否读取；无虚构工具能力 |
| F02 | 同一组件 | Web和Electron使用同一React入口/组件，不维护独立demo产品 |
| F03 | 真实后端 | 一次UI创建/编辑在磁盘可读，刷新仍在；服务类型如实显示 |
| F04 | 实例隔离 | 两个worktree/测试实例根、端口、profile、发现信息不串 |
| F05 | HMR | 改样式后可直接观察，不重启受控session、不重复录制或写资料 |
| F06 | API主体 | 未配对/错误Origin/旧凭据拒绝；业务Agent权限不因WebUI上线扩大 |
| F07 | 代表编辑流程 | 卡片复制、字段编辑、普通注释、固定版正常路径成立且返回正确ID |
| F08 | 冲突/重连 | 断连后不假报取消；幂等重试不重复创建；旧回执不抢新对象 |
| F09 | 默认与窄窗口 | 至少1450×935与1100×760；滚动、长文本、错误和加载状态均能正常操作 |
| F10 | 命中与焦点 | 控件非零尺寸、在裁切范围内、实际命中自己；modal焦点与Esc正常 |
| F11 | 可读性 | 主要业务名而非UUID占主位置；当前对象、只读/编辑和保存状态明确 |
| F12 | 壳冒烟 | 新UI仍在Electron运行；启动、旧资料、native surface、停止/退出无回退 |
| F13 | 回放入口边界 | 已迁Web播放则验证真实DOM与来源；未迁则明确仍需native，不用截图冒充 |
| F14 | 报告归属 | UI源码、后端源码、构建/实例、测试模式分别记录；旧成绩不外推 |

以下是B2/B3扩展门，不是B1可伪造的完成项：

- Web回放顺播/精确seek/节点选择，配对消息的过期回执拒绝；资源隔离和恶意录制负例。
- 纯Node启动没有Electron runtime；专用Chromium target从导航前完整采集，必要多frame能力真实测。
- 旧Electron profile仍可打开，新Chromium profile不覆写它；关闭/取消行为双provider一致。
- 同一固定资料正确值pass、错值fail、无来源inconclusive；示范与执行证据不混同。

## 7. 如何判断此次改造是否值得继续

不以新增接口、测试数量或代码行数判断。比较同样三个代表任务的开发过程：

- 从一处UI修改到实际看见结果，需要哪些步骤，花在构建/窗口/人工输入上的时间有多少。
- 多少问题能由DOM/样式/请求直接定位，而不靠猜坐标或让用户截图转述。
- 成功场景是否需要额外手工解释按钮、重复选择或直接内部命令修数据。
- 普通开发能否并行独立实例，而不用所有人等待唯一OS桌面。

这些值从本次启动和任务日志记录即可，不另做监控产品。没有准确token明细则不估算；不承诺固定速度倍数。

若B1仍需要大量OS控制才做普通表单，先修观测入口，不继续铺完整Node架构。若已经明显改善，可以接B2；B2历史场景稳定后再决定B3的外部运行时是否有额外收益。最终业务页面手工登录需要外部窗口，并不意味着工作台Web化失败。

## 8. 分工、Git和退出条件

首批一个负责架构纵向与实现的Agent即可；接口冻结后，可有一个独立助手做Web场景测试或隔离的UI模块，禁止两人同时修改App/Studio/公共客户端。不要重新开L/R/P及全部旧分支。

代码和相关文档按可验收包提交，测试fixture和短执行说明进入仓库；截图/trace/录制/真实profile留在忽略的测试输出。Git、等待和日志摘要直接工具执行，主控不重复助手的全量review。

本次用户只要求评估时不自动修改其仓库；用户粘贴配套实施提示词后才开始B0/B1。实际工具不能完成的授权请求最小化。B1完成后给出可运行URL、三场景证据、后端依赖事实和收益评估，再由用户决定是否立即扩到B2/B3；不要连续几小时只增加基础设施而不给可操作页面。

源规范无需增加更多编号。更新`docs/README.md`为本决策/反馈循环入口，AGENTS只补两条稳定规则，详细阶段留在这里。
