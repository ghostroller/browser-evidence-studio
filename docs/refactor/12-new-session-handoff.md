## 1. 项目究竟要做什么

这是一个本地 Electron 网页采集开发工作台，供人和外部编码 Agent 协作，不是单纯录屏工具，也不是依赖 LLM 才能运行的 RPA 流程平台。

目标流程：

```text
独立打开并准备登录环境，不录制登录过程
→ 开始业务示范，连续保存 DOM 变化和相关证据
→ 用户创建保存点，实时或在历史回放中选择元素
→ 给保存点添加说明、需求、字段和可选元素示例
→ 固定一份任务资料版本，交给外部 Agent
→ Agent 交付普通 Puppeteer 代码与技术映射
→ 使用明确的环境和输入执行，保存部分结果和来源
→ 用户看懂正确、错误、未核验及其原因，能跳回材料
```

### 不可混淆的对象

| 对象 | 含义与边界 |
|---|---|
| 项目/任务 | 用户要完成的业务目标，不随某次录制消失 |
| 登录环境/profile | 环境配置及持久浏览器状态；打开环境不能强制创建示范录制 |
| BrowserSession | 当前实时页面、导航、控制权；录制和执行附着于会话 |
| Recording / receipt | 原始观察与采集收据，不因说明编辑而改写 |
| 保存点卡片 | 对某个历史位置的可编辑说明，可关联需求；不是第二套原始录制 |
| Requirement / Field | 用户要求与字段语义，元素绑定和附加注释均可选 |
| 工作草稿/固定版本 | 草稿可编辑；固定版按内容 hash 读取，旧版不能原地修改 |
| 实现映射 | Agent 提出的输出路径、来源匹配与允许的值解释，不得悄悄改变用户语义 |
| Execution / attempt | 实际执行及尝试，固定任务版本、代码、输入与来源身份 |
| 机器/人工判断 | 分开追加；执行完成、机器通过和人工接受不是同一状态 |

技术基础已存在：React 工作区、Electron 原生页面、rrweb 录放与源节点身份、资料服务、受控 worker、耐久批次、固定报告、范围授权。**保留这些基础，针对本批问题修改。**

## 5. T1：值语义与来源核验

### 5.1 目标和当前根因

正确链路应为：

```text
原始可见文本「45.00」
+ 用户固定语义：金额、number、依据页面显示
+ 已明确声明的纯十进制解释规则
→ 宿主从原件独立得到 45
→ 对比脚本输出，并保留原始文本和来源身份
```

当前 `DomTextSourceProof` 没有数值解释契约；`implementationMapping()` 解析了 proof，但没有检查它与字段类型的兼容性；`displayedFieldProof()` 在检查来源之前要求输出与实体键均为 string。这里不能只换一个比较运算符。

定位：

- `src/contracts/workflow.ts`：proof 类型与解析。
- `src/materials/validate.ts`、`src/materials/service.ts`：资料验证和固定内容 hash。
- `src/main/services/implementation-mapping.ts`：映射预览/确认。
- `src/validator/proofs.ts`、`service.ts`、`types.ts`：字段证明、类型与诊断。
- `test/unit/dom-source-proof.test.ts`、`validator-materials.test.ts`：既有约束。

### 5.2 实现路径

1. 在现有 proof/mapping 上增加显式、可版本化的值解释模式。名称由实施者按现有契约确定，例如 `plain-decimal v1`；这是示例命名，不是假定已有 API。
2. **未声明新模式的旧 `dom-text` 继续精确文本比较。** 不在读取旧资料时回填默认字段，不改变旧 hash 或旧报告。
3. 实现小型纯函数：解释规则解析、映射兼容检查、有界数值规范化与比较。只解决本批纯十进制需求，不引入任意 JS、表达式链、任意正则或 LLM 裁判。
4. 预览和确认复用同一兼容检查：`number + 旧 exact-text` 明确不可兼容；普通任务尚无技术映射时仍可保存草稿。正式核验前再次检查准确的固定版本，探索试跑与可核验状态分开。
5. 宿主从真实录制的 display sample 独立计算，继续检查执行/attempt、页面/frame、时间、可见性、语义属性和实体身份。不得信任脚本自报的 normalizedValue，也不能从当前网站或回放 DOM 补造原件。
6. 映射摘要用普通语言展示源例子、输出类型、解释模式和限制。用户不手写 proof JSON，也不被要求为了工具能力改掉正确的数值语义。
7. 用正常 UI 从现有失败资料派生新版本、确认新映射再执行。旧 V1/V2/V3、失败报告与原件保留。

### 5.3 纯十进制模式的最小边界

实现前写明并测试完整语法、是否接受首尾空白和符号、长度/范围及精度策略，不能让 JS 的宽松转换决定语义。

- 支持 `45.00 → 45`、`12.30 → 12.3`；源字符串仍可查看。
- 不进行部分解析；空串、遮罩、破折号不能变成 0。
- 默认不猜币种、百分号、千分位、小数逗号、万/亿单位或括号负数。
- 排除非有限值及可观察的精度丢失；不通过 epsilon 容差掩盖真正不一致。
- **只解释字段值，不解释实体身份。** `"0012"` 与 `"12"` 默认是不同实体。
- 新格式需求以后另加声明和测试，不能暗中扩大 v1。

### 5.4 必须保持的判定区别

| 输入与前置 | 结果 |
|---|---|
| 显式数值映射，来源 `45.00`，输出 45 | 类型 pass、来源 pass |
| 同来源，输出 46 | 类型 pass、来源因实际值差异 fail |
| 合规数字，真实 `sourceRefs=[]` | 类型 pass、来源 inconclusive |
| number 任务输出 string | 类型 fail；来源缺失不能冲掉已证实的类型错误 |
| number 配旧精确文本 proof | 映射不兼容，不伪装为已观察到业务错误 |
| 旧 exact-text：源 `￥12.30`，输出 `12.30` | 保留旧 fail |
| 来源缺失/遮罩/语法不适用 | 不猜期望值；明确未核验原因 |

诊断应分别说明“配置不相容”“输出类型错误”“依据不足”“值不一致”。规则版本或等价标识进入新报告，旧报告仍按原记录解释。

## 6. T2：编辑与采集中断恢复

### J02：采集前保护已有编辑，但不阻断未完成的新字段

复现：修改已保存卡片 A 的说明但不保存，点击“记录当前结果”或实时字段选择；新卡 B 返回后，检查 A 的编辑是否丢失。当前 `recordCurrent()` 成功回执会替换卡片表单，而它没有完整经过 `changeEditor()` 的 dirty 处理。

修正应建立统一的编辑交接入口：旧卡片的有效 dirty 说明/关联先提交，失败不切换；尚未完成的新字段可能正需要先选元素，保留其缓冲，不强制所有表单先合法保存。分别固定旧卡片、字段编辑、所属需求、新样例的身份。

回归不只断言 B 保存成功，还要检查 A 的修改、B 的原件与 F 的绑定全部正确；取消、过期、partial 和重试也不能覆盖旧缓冲。

### J03：字段归属不能由事务处理顺序决定

复现：字段区域选择需求 R1 并编辑/新建 F，同时在卡片区域填写新关联需求 R2，直接发布。当前 `saveEditor()` 的单一 `nextRequirement` 可能先被 link 分支替换成 R2，再接收 F。

修正：明确区分字段所属需求、需求说明补丁、新关联需求和卡片链接。事务先固定对象身份，再合并 patch；不能依靠同 ID 的多个 upsert 先后顺序表达关系。

只有用户明确选择“F 属于这次新需求”时才建立这个关系。正常默认仍属 R1。测试新/已有 F、R1 的既有 F0、R2 和卡片关系，不能只看 CAS 成功。

### J04：区分活跃采集与中断后留下的磁盘阶段

复现：journal 已写 `acquiring`、receipt 尚未完成时终止隔离测试进程；重启后查询 operation，检查是否永远停在 acquiring 且锁住资料编辑。

修正路径：

1. operation 关联 appInstance/session/operation 身份，并登记当前实际执行任务；PID 单独不能证明原执行者仍存在。
2. 恢复首先按 operationId 查原始 receipt。存在且身份正确则幂等关联，不重采。
3. 确认旧执行者已经结束且没有 receipt 时，转明确 interrupted/source-expired 等可恢复终态，允许新操作；不能把旧现场当成仍可继续采集。
4. 原件读失败不是“确定没有 receipt”。保留 unknown 和诊断，但提供离开当前恢复、编辑无关对象的路径，不永久锁全工作区。
5. 活跃任务不能仅因查询超时就被当作死亡；需要明确取消/收尾或存活证据。
6. journal、部分 artifact、原件全部保留，不通过删除旧操作或向封存 run 续写解锁。

故障注入边界：意图之后、acquiring 之后、artifact 已写 receipt 未写、receipt 已写关联未写、关联已写 journal 未收口。模块测试可直接构造故障；产品路径不得靠写文件补成功状态。

- 数值不匹配能展示实体、原始 `45.00`、规则、应得 45 与实际 46；没有来源则不造一个期望值。
- 保留有界、可追踪诊断身份：fieldId、entity、dataset/attempt/batch/recordIndex、outputPath 和来源引用，详细材料按需加载并遵守隐私规则。
- 不只给内部 UUID、英文规则名和 JSON；普通界面应解释问题与可执行下一步。

覆盖语义需分清：数据已提交完整，不等于“全部订单”已经被证明。已有 `coverage=complete` 无法单靠空的分页规则集合证明自然语言全量目标。保留旧报告，新增或调整展示使“批次提交完整”“已配置检查结果”“业务范围尚缺证明”可区分。

对明确“两条且不重复”的任务，通过正常资料配置表达必要约束。只返回一条/两条重复不能与全部正确得到同样的业务完整结论。**不得把合成站点恰好两条硬编码成通用规则。**

## 8. 调度与成本：最多两个实施者，不新增管理层

默认当前会话直接实施并集成。当前模型通过客户端实际设置；不要在提示词里声称切换就算配置生效。

确实有可独立开展的工作、且工具支持安全工作目录隔离时，可以启动 **一个额外实施任务**：

| 范围 | 唯一所有者与交接 |
|---|---|
| T1 proof/validator/映射后端 | 一个 owner 负责共享类型、解析和判定；接口一次说明清楚 |
| T2 编辑/采集恢复 | 一个 owner 负责 MaterialWorkbench 和 Studio authoring；需要 T1 的 UI 接入由这个 owner 完成，禁止双写 |
| T3 UI 导航与产品验收 | 接已集成接口；独立验收安排在可用槽位，不再增加常驻协调层 |

没有适用的子任务工具就单流继续，不另建调度平台，不要求用户逐个开会话。保持有效上下文；不要每次小返修就创建新 Agent 重读项目。

Git、日志摘要和提交核对直接批量调用工具。实施者按可验收包提交；交流只需交付、真实阻塞和共享契约决定。限定范围审查不再被主控完整重复一次。

所有 Electron/物理输入测试使用一个桌面令牌；测试使用冻结源码和构建，同一树不能边测边合并重编。其他流可以进行不冲突的编辑/定向测试。完整日志落盘，成功只报命令/退出码/数量/路径，失败读取首个有效错误与必要上下文。

T1→T2→T3 按依赖自动推进，不每包等待用户说“继续”。有真实权限、额度或不可逆决策阻塞时提出最小请求；无关部分继续，不虚报完成。
